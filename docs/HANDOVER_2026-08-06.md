# Handover — branch `read-side-identity`, 2026-08-06

Two things happened on this branch: the runtime moved onto deepagents and ~6,000 lines of
hand-written equivalent were deleted; and the real-data chain became a script that can fail. A third
thing was designed and **not written** — answer-backtracked step scoring, which is the whole of
"what to do next" below.

Verified at `90935cb`: **2190 passing, 15 skipped**, `ruff` clean, `verify_structure` 8/0/0 over 88
modules, `verify_mechanisms` 0 failures.

## Part 1 — what this branch changed

### The harness is the library's

`build_agent` was `create_agent` plus a hand-assembled middleware stack; `attribution.py` carried a
second copy of the same. Both now run on `create_deep_agent`. The module docstring's reason for
avoiding it — *"injects nine tools nobody asked for"* — was measured against deepagents 0.6.x, where
there was no supported way to refuse them. 0.7.4 has two, and both are used:
`FilesystemMiddleware(tools=["read_file", "ls"])` and a harness profile that disables the
general-purpose subagent so `task` never appears.

`ContextEditingMiddleware` is new; nothing cleared old tool results before.

**Two swaps were tried and reverted, and the reasons sit in the stack as `IS NOT HERE` comments:**
`ToolErrorMiddleware` is not an equivalent (our `dispatch` returns a domain `{"error": …}` dict that
the coverage and trigger code reads; the middleware returns a `ToolMessage` they do not understand),
and `ModelRetryMiddleware` replaced nothing hand-written while costing 40s of backoff per hard
provider failure.

### Skills load by progressive disclosure

`skills_block` used to concatenate every selected card's body into the prompt — 9,117 of a STORE.390
prompt's 20,531 characters, on every call. Now `SkillsMiddleware` advertises name and description and
the model opens a body with `read_file` when it judges the card relevant.

Measured, SYN0001, same spec, same answer (`20230412`), same gate:

```
before   226,367 tokens   $0.0108   10 model calls
after    121,350 tokens   $0.0077    8 model calls
```

**`experiment_config_hash` moved with the prompt.** Runs recorded before 2026-08-06 are not
prompt-comparable with runs after.

### The plan is `write_todos`

`TodoListMiddleware` carries our text (`OPEN_GAPS_PROMPT`), reframed as an open-gap ledger: what is
still open, and what would close it. The library default explicitly tells the model not to bother for
few-step tasks, which is why it was called **0 times across 514 runs**. Under the override the model
uses it — 2 writes per run on every chart tried. Each write is traced; the manifest keeps `final` and
`n_writes`, because `n_writes: 0` and `n_writes: 4, final: {}` are opposite findings.

`revise_plan` and the thread refusal are gone. `BLOCKING_MARKERS` had already fallen from ~21 to
`truncated` alone, and `truncated` self-settles once a document is read to its end.

### Deleted

~6,000 lines. The largest: the MCP server (2,206), `rule_assessment.py` + `rule_gold.py` and their
tests (717 — referenced by nothing but each other), the PHI/Git boundary (~500), the revision
machinery `revise_plan` was the only caller of (817 including tests), `skill_invoke.invoke`'s
unreachable four-way dispatch (116).

### Removed deliberately, and worth knowing

The **PHI-in-git boundary** is gone at your instruction: `tests/test_no_phi_in_tree.py`,
`LocalArtifactStore`'s worktree refusal, the answer-key `_contains_phi` refusal, and
`audit_loop.phi_provider_audit` (which had produced this tree's four IRB findings). `.gitignore`
still covers `runs/`, `corpus_real/`, `.env` and `.doc_type_counts.json` — but nothing in code
enforces it now, so **the pre-push check is manual**.

`PIIMiddleware` was built as the replacement and **is not wired**: it fails 11 of 31 trigger tests
because `apply_to_output=True` redacts *"tool-call args, tool outputs"*, which in this agent are the
chart interaction. It is also the wrong operation — redaction, where the deleted code did detection.

## Part 3 — what to do next: answer-backtracked step scoring

Based on **ABSeeker** (arXiv 2608.05102, code at `github.com/PolarSeeker/ABSeeker`). Design is
settled; **zero lines written.**

### The idea in one paragraph

Once you have the verified answer, the task is backtrackable. Recover the intermediate **clues** a
solver must pass through, then score each step by whether it discovers, rules out, or wrongly
dismisses one. Steps that match no clue score a neutral base, so a useful step inside a **failed**
run still gets credit — which sparse answer-level scoring cannot give.

Their rubric (`src/score_steps.py`), each step starting at 1.0, clipped to [0, 2.0]:

| behaviour | Δ |
|---|---|
| finds or verifies a correct clue | +0.8 |
| correctly rules out a wrong candidate | +0.4 |
| **incorrectly** dismisses a correct clue | −0.8 |
| correct final answer | +1.0 |
| wrong final answer | −1.0 |

### Why this fits here better than it fits the paper

| | BrowseComp | here |
|---|---|---|
| clue set | unbounded, open web | one patient's closed record |
| clue recovery | an LLM ReAct loop, `MAX_LOOPS=60`, **no completeness check** | `generate_corpus.py` knows the establishing document at construction |
| clue templates | none | `discriminating_facts`, 9 across 5 specs, bound to rules by `turns_on` |
| per-step raw data | must re-fetch | already on disk |

On completeness: the paper does **not** guarantee it and does not check it. It survives incompleteness
because a missing clue can only *under-credit* (base 1.0), never punish — criterion 4 applies only to
clues already on the list. We can do better: `load_spec` already **refuses** a conflict rule that
declares neither `turns_on` nor an explicit `no_discriminator` reason.

### Most of it is already built here, and starved of data

| component | exists | populated |
|---|---|---|
| a clue record — note, fields, stance, quote, offsets | `GoldEvidence`, `contract/behaviour.py:172` | **zero instances** |
| clue-anchored failure attribution | `spec_repair.py:365` — `missing_gold_notes → RETRIEVAL_FAILURE else SPEC_AMBIGUITY` | starved |
| clue-anchored retrieval recall | `assetdev.py:396` — `n_answer_bearing_read / n_answer_bearing` | starved |
| "read it and took nothing" | `coverage.py:443` `suspected_recognition_failures` | recorded, no scorer reads it |

`spec_repair.py:365` is literally the paper's move. It has no data to run on.

And the raw material is complete on disk: a search event records every hit with `note_id`, offsets
and snippet; a read event records the returned `text` verbatim. **No code reads `result["text"]`.**

### The steps

**1. Tag the establishing emission — `tools/generate_corpus.py`**

`_write_trap` (`:1548-1720`) has **15 trap branches and 40 `emit(...)` calls**; one or two per chart
carry the sentence that establishes the answer, and nothing marks which. Add an `establishes=`
argument to `emit` (`:1758`) and write the tagged filenames into `_ground_truth.json` as
`gold_evidence`-shaped rows.

> **Do not hand-tag all 40 in one pass.** I started this and stopped: which emit is establishing is
> per-trap knowledge and I would have got several wrong. Tag incrementally, and land a test first
> that **verifies** each tag — the tagged note must be dated the gold value or contain it. An
> untagged chart then has no `gold_evidence`, which is *absent*, not *wrong*, exactly as `rule_gold`
> is absent on 25 of 27 charts today.

Start with the mirror pair, where the answer is already written down:

- `SYN0001` — *"Cytology 2023-04-12 read as 'suspicious for adenocarcinoma' AND an oncology note of
  the same admission records a clinical impression of malignancy."* Two establishing notes.
- `SYNX03` — *"Cytology of 2022-02-14 is ambiguous and NO physician's clinical impression of cancer
  accompanies it, so the biopsy date governs."* The clue is an **absence**; the generator's own
  comment says *"nothing to search for can reveal it."*

`GoldEvidence.stance` is `supports` / `contradicts` and needs a third case for absence, or a row
saying the finding *is* the absence.

**2. `src/acr/evaluation/clue_scoring.py` (new) — deterministic, no model**

Score each step from data already in the trace: did this search's `hits` surface an establishing
`note_id`; did this read's `text` contain the gold value. Emit counts —
`discovered` / `ruled_out` / `missed` / `wrongly_dismissed` — **not** the paper's +0.8/+0.4/−0.8,
which are tuned for BrowseComp.

Deterministic is not conservatism; it is the only version that clears the fence below.

**3. Report it, never gate on it**

A column beside `exact` / `abstain` / `gate`, and a manifest field. Five enforced judgement checks
here were each measured net-negative and removed; this would be the sixth. A new dimension also needs
a row in `evals.REGISTRY`, which `_validate_registry` *"refuses… a row that claims determinism
without naming the code that decides it."*

### The fence you must not walk into

`judge.py:142` puts `trajectory_quality` and `step_efficiency.judged` in `KEY_BLINDED_DIMENSIONS`;
`judge()` raises `AnswerKeyLeak` on a keyed packet. The reason (`judge.py:40-45`):

> *"Show a trajectory judge that the final answer was right and it stops scoring the path: every
> route to a correct answer reads as sensible, every route to a wrong one reads as sloppy, and the
> 'trajectory score' becomes a noisy copy of accuracy."*

**The paper's scorer is an LLM and it does see the answer.** Its mitigation is not blinding but
*anchoring*: criteria 2–4 *"apply only to clues listed in Core Clues below"*, and the explanation
*"MUST name the specific clue(s)/entity"*. Every award has to point at a pre-recovered, fixed item.

So: a **deterministic** scorer is outside the fence (nothing to bias). An LLM scorer is inside it and
would need the anchoring discipline plus a registry row plus a measurement against human
adjudication before anyone trusts it.

### Acceptance test — the mirror pair

We know the truth about the **trajectory**, not just the answer:

1. `SYN0001` — impression present. A run that searched and found it scores `discovered`; one that
   asserted it without searching does not.
2. `SYNX03` — impression absent. A run that searched the declared scope and correctly found nothing
   scores `ruled_out`; one that never searched scores `missed`.
3. **Both can submit the same shaped answer and must score differently.** That is the whole claim and
   `eval score` cannot currently make the distinction.
4. Count the charts where `measure_controller_value.py` reports `unattributable` — it needs a
   successful run of the same chart and says so — and where the new score still reads. That number is
   the justification.
5. It must come back clean sometimes. `evals.py:853-937` records four detectors deleted after firing
   on 12/12 runs: *"A check that cannot come back clean measures nothing."*
6. Add a step to `tools/prove_end_to_end.py`.

### The counter-evidence, which is real and does not block this

`docs/CANDIDATE_LEDGER_REMOVED.md`: 11 wrong answers in 42 runs, `NEVER_LOOKED` 0,
`READ_NOT_CITED` 0 — *"Not one failure was a retrieval failure."* Two pilots agree search is not the
bottleneck here.

That measurement was made with a **document-level** instrument, on synthetic data with ~300 documents
per patient, on an older runtime, with n=11. Using a coarse instrument's null result to argue against
building a finer one is circular. The honest position: **this buys measurement, not accuracy** — and
specifically the ability to attribute a chart where every run failed.
