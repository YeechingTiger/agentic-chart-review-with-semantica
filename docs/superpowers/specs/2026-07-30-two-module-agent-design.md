# 两个模块：跑病历的，和评测的

**日期**：2026-07-30
**状态**：设计已定，待实施

这份文档正文用大白话写。代码里的名字**一个都不改**（`spec`、`trace`、`gate` 这些照旧），
因为 `spec_hash`、`SPEC_INSUFFICIENT`、`gate_validated` 这几个字段已经写进了所有历史存档，
改了以后过去的 run 和以后的 run 对不上账。文档末尾有对照表。

---

## 1. 一句话

**一边跑病历出答案，一边看这些答案跑得对不对。评测这边分两种做法——死板的程序算，和 AI 看
工作记录找原因——两种都产出同一种东西：信号。**

---

## 2. 模块一：跑病历（run）

### 它干什么

打开一个病人的全部病历，按规定找出要填的几项（长在哪、什么类型、良性恶性），每一项都要
指出是在哪份报告的哪句话里看到的。指不出来就不许交答案。

**这块基本已经做完了**，`acr run` / `acr batch` / `acr extract` 都能跑。这一期只补一个洞。

### 它上岗带三样东西

**一、填表规定**（代码里叫 spec）
写死的、医生签过字的、锁死的。规定这次填哪几项、什么值算对、什么记录够格当依据。
**机器人只能照办，不能改，也不能不听。**

**二、经验卡**（代码里叫 skill，这个词保留，因为是目录名 `assets/skills/*/SKILL.md`）
不是规定，是"老手怎么干这活"。机器人可以不照做，但要在工作记录里写清为什么。

分三个槽，一个槽装一类：

| 槽 | 装什么 | 带几张 | 现有的卡 |
|---|---|---|---|
| `task` | 这个活怎么干 | 0–1 张 | `store-icdo-coding`、`store-staging` |
| `search` | 病历怎么翻 | **恰好 1 张**（可以是"什么都不给"） | 待建 |
| `general` | 任何病历都用得上的功夫 | 若干张 | `chart-triage`、`thread-chasing`、`coverage-judgement` |

**为什么"病历怎么翻"要单独占一个槽、一次只装一张：**
这样才能做干净的对照试验。同样的病人、同样的规定、同样的其他卡，**只换这一张**再跑一遍，
两次结果的差别就纯粹是这张卡带来的。混在一起就永远不知道是哪个变化起的作用。

`docs/SEARCH_PLANNING_PILOT.md` 已经证明这种对照是刚需：以为有用的检索经验，实测下来
准确率反而低一点（4/10 对 3/10）。没有干净对照，这个结论根本得不出来。

**三、工作记录**（代码里叫 trace）
每一步都记：搜了什么词、翻了哪几份报告、为什么下这个结论、花了多少钱。

### 要补的洞

技能槽的机器**已经在了但是空的**：`runtime_profiles.py` 里的 `_PROFILE_SKILLS` 是个空字典，
所有 profile 都退回同一张 `coverage-judgement`。所以现在**换 profile 并不会换经验卡**，
对照试验换的只是别的东西。

补三件事：

1. 每张卡的开头声明自己属于哪个槽（`slot: task | search | general`）。装错槽直接报错，
   不许静默通过。
2. `_PROFILE_SKILLS` 按槽填上，加载时校验：`search` 槽多于一张 → 报错。
3. 命令行加 `--skills` 参数，不用新建 profile 就能临时换一张卡，方便做对照。
4. 存档单里按槽分别记每张卡的内容指纹——两次 run 换了哪个槽，一眼看得出。

### 新建的"病历怎么翻"卡

先落两张，对应已经跑过的两个试验臂：

- `search-native`：自己看着办，觉得查够了就停
- `search-preplanned`：先按以前统计的经验排个顺序再查

以后加策略就是加一个目录，不改代码。

## 3. 模块二：评测（eval）

### 它干什么

它不看病人、不填表。它看的是**跑病历那边留下的工作记录**，外加一样跑病历那边绝对看不到的
东西：**标准答案**。它回答"这次为什么对了，那次为什么错了"。

### 两种做法，一个出口

这是这一期最要紧的结构。评测分**三种做法**，回答三个不同的问题，但**产出同一种东西**：

```
              工作记录（+ 标准答案，只有部分做法能看）
                │
      ┌─────────┼─────────┐
      │         │         │
  程序算的   AI 评卷    AI 归因
  （死板）  （看过程，  （找错因，
            蒙着答案）   拿着答案）
      │         │         │
      └─────────┼─────────┘
                ▼
             信号
```

| | 回答什么 | 能看标准答案吗 | 权限 |
|---|---|---|---|
| 程序算的 | **对不对**、越没越线 | 能 | 可以拦截、可以立案 |
| AI 评卷 | **过程规不规范**（没有标准答案可言的事） | **不能** | 只能打观感分、排顺序，永远不是闸门 |
| AI 归因 | **为什么错** | 能（就是靠对照答案找原因） | 只能出诊断报告 |

这三种正好对上方法论文档（`AGENTLOOP_TO_ACR_METHODOLOGY.md` §2.6）记录的 AgentLoop
执行方式：CODE → 程序算，LLM → AI 评卷，AGENT → AI 归因；第四种 HUMAN（临床裁决、
确认 gold）在命令行之外，保持不变。

"信号"这个东西代码里已经有了（`kernel.py` 的 `SignalEnvelope`），带证据指针和严重
程度。三边都往这个格式里写，下游就只认一种东西。**程序算出的分和 AI 打的观感分
在信号里带不同的标记，永远不许平均到一起**——这条 `judge.py` 已经写死了。

#### 做法一：程序算的（不用 AI）

一是一二是二，跑一百遍结果一样。**已经有了**（`evals.py`、`audit_loop.py`）：

- 答案和标准答案**一样吗**——就是 `==`，不是"相似度"
- 引用的原文**真的在那份报告的那个位置吗**——回原文核对
- 有没有报告翻到一半就断了
- 花了多少钱、调了多少次模型
- 有没有已知的异常行为（比如反复搜同一个词卡死）
- 有没有越线（串病人、隐私外泄、用了没申报的工具……）

#### 做法二：AI 评卷（看过程，蒙着答案）

这条线评的是**工作记录本身的质量**——AgentLoop 叫 agent-as-a-judge，评的是
trajectory，不是归因。它回答的都是**没有标准答案、也没法数数**的问题，程序和
答案钥匙都帮不上忙。**已经有了**（`judge.py`），五个可评维度，每个维度配三个
固定的"镜头"（一个镜头 = 一个专门盯一种失误的问题）：

| 维度 | 三个镜头各盯什么 |
|---|---|
| **翻病历的路子**（trajectory_quality） | 读的顺序合不合理（决定性的报告是不是拖到最后才读）；提出过的疑点有没有跟丢；力气花得配不配（过度和不足都算） |
| **证据到底撑不撑**（evidence_support 的判断半） | 引的那句话是**陈述**了编码值还是只沾边；**没读过**的文档里有没有唱反调的；把"倾向于/不排除"这种含糊话当成定论了没有 |
| **每一步值不值**（step_efficiency 的判断半） | 只用当时已知的信息看，下一步走得合理吗（防事后诸葛亮）；有没有更便宜的一步能更早解决；答案已经定了之后还花了多少冤枉钱 |
| **解释的质量**（l5_explanation_quality） | 断言的每个原因在记录里有没有依据；别的候选原因排除了没有；口气比证据大了没有 |
| **坏案例排序**（bad_case_triage） | 人看这个案例能学到新东西吗；是会重复出现的一类还是一次性的；查实了能改什么 |

**两条铁规矩，都已经在代码里钉死：**

1. **评卷员看不到标准答案**（坏案例排序是唯一例外，它的任务就是排已知的错案）。
   原因：让评卷员知道最后答对了没有，它就不看过程了——通向对答案的路全被打成
   "规范"，通向错答案的路全被打成"潦草"，过程分就成了准确率的复读机，而准确率
   程序已经算得更好。
2. **观感分只能用来筛查和排序**（哪些 run 值得人先看），永远不能当闸门拦答案，
   也永远不和程序算的分平均。

**扩展方式：加一个评卷角度 = 加一个 `assets/evaluators/` 下的 YAML 文件，不改代码。**
这是 `judge.py` 自己定的规矩（往内置字典里加镜头 = 改代码 + 部署 + 领域专家没法
签字确认）。YAML 里声明评哪个维度、问什么问题、需要什么材料；加载时围栏自动核查
——一个声称要判"正确性"的评卷 YAML 会被**拒绝加载**，因为正确性有程序在算。
它和经验卡是同一个思想（加文件、不改代码、可签字），格式不同是因为评卷需要机器
可查的结构：维度名要对着注册表核查，材料要按声明注入。

#### 做法三：AI 归因（找错因，拿着答案）

程序只能告诉你**"错了"**，评卷只能告诉你**"过程哪里不规范"**，都告诉不了你
**"这个错是什么造成的"**。找原因要通读工作记录、提出候选解释、回病历里找区分
证据——这是归因 agent 的活（`attribution.py` 的八段流程，见前文）。
**每一种诊断思路 = 一张经验卡**（`slot: eval`）。

先落四张：

| 卡 | 干什么 |
|---|---|
| `eval-contrast-traces` | 把答对的和答错的工作记录摆一块，看搜索词和顺序差在哪 |
| `eval-cluster-failures` | 十个病人错了六个，是同一个毛病还是六个毛病 |
| `eval-missed-evidence` | 答案其实躺在某份报告里，为什么没翻到那份 |
| `eval-overconfidence` | 答得斩钉截铁但答错了，当时凭的什么 |

**加诊断角度 = 加一张卡，不改代码。**

#### 方法论文档的六个评价领域，各归哪条线

`AGENTLOOP_TO_ACR_METHODOLOGY.md` §2.6 定义了六个评价领域，全部有着落：

| 评价领域 | 归哪条线 |
|---|---|
| 安全与边界（隐私、串病人、外发、越权） | 程序算（审计 6 项） |
| 结果与弃答（值对不对、该弃没弃） | 程序算（判分 7 项） |
| 证据与依据（引文、文档资格、没读到的矛盾） | 程序算（引文核对）+ AI 评卷（证据支撑三镜头） |
| 过程与控制完整性（交卷检查/台账/终止一致性） | 程序算（检测器 + 审计） |
| 可靠性与效率（重试、成本、延迟、阅读量） | 程序算（资源区间）+ AI 评卷（步骤效率三镜头） |
| 因果归因（哪个缺陷解释这个错、该修哪类资产） | AI 归因（八段流程 + 诊断卡） |

### 一条不能破的规矩：判分不许交给 AI

**"答得对不对"只能用程序算，AI 没有这个权力。**

为什么这条要写死在代码里而不是靠自觉：AI 判分会出一种特别阴的错——

> 病历里确实没写，机器人老老实实答"证据不足"。**这是对的行为。**
> 但 AI 判分器会觉得"你没完成任务"，扣分。
> 长期拿这种分数调教机器人，等于教它**碰到不确定就编一个**。
> 而不确定的病例，恰恰是最不能编的。

所以怎么落地：

- 评测 AI 的工具箱里**根本没有**一个"我宣布这题答错了"的按钮。它想知道对错，
  只能调用程序去问。
- 每张评测卡开头声明自己**允许判断哪几类问题**（`judges:`）。声明之外的判断，
  lint 能查出来。
- 现有的 `judge.py` 围栏（有确定性检查的地方禁止用 AI judge）继续有效，一个字不改。

### 单个和批量都要能跑

现在的现状是**能跑但入口是散的**：`acr eval` 一套、`acr audit` 一套、`acr evaluation`
一套、`acr attribute` 一套（这个已经有 case 和 batch 了）。

这一期做一个统一入口，把三种做法都收进来，单个和批量都有：

```
acr signal run    --kind rule   ...    单个，程序算
acr signal run    --kind judge  ...    单个，AI 评卷（--dimension 选维度，蒙着答案）
acr signal run    --kind agent  ...    单个，AI 归因
acr signal batch  --kind rule|judge|agent ...    批量，同上
```

**为什么叫 `acr signal` 而不是塞进现有的 `acr eval`：** `cli_eval.py` 开篇就承诺
"这个组里没有一条命令会调模型"，`evals.py` 还有测试走 import 关系图钉着这句话。
AI 复盘要调模型，加进去就把那句承诺变成了一句留在纸上的空话。所以新开一个组，
名字用你自己的说法——两种做法都产出信号，这就是问信号的地方。

旧命令**全部保留不动**（`acr eval`、`acr audit`、`acr attribute`），新入口是薄薄一层壳，
底下调的是同一批已经测过的代码。

## 4. 两个模块必须隔开

评测那边看得到标准答案，跑病历那边**绝对不能看到**——不然测出来的准确率是假的。

两边不在同一个进程里跑，现在就有测试卡着这条线（`tests/test_evals.py` 走 import 关系图，
发现跑病历那边能摸到标准答案就失败）。继续留着，不动。

## 4.5 从 DeepEvidence 借来的四项（Task 10–13）

读了 DeepEvidence 那套深度研究智能体之后，有四件事值得搬进来，也有一件明确不要搬。

**（1）每一次读都记下"为什么读它"。** 现在的工作记录是一串平铺的事件，事件之间**没有
连线**。归因 agent 被要求"分清记录证明的和推测的"，但"第 9 步读了 D12，是因为第 7 步
搜索返回了它"——这在平铺记录里永远只是**根据前后位置猜的**，而报告不会说它是猜的。
加一个可选的"因为什么"字段（不填不拒，但**数出来**：有成因的读占多大比例），归因第一步
就从推断变成查表。改动很小：工作记录本来就把工具参数整个记下来了，只要在说明书里问，
模型就会填。

**（2）三种翻病历的走法，做四臂对照。** DeepEvidence 的消融结论是：**只撒网不够、只顺藤
摸瓜也不够，两者结合才最好**。你们的 pilot 比的是另一根轴（计划从哪来），走法的形状
从没测过。而且**顺藤摸瓜这套你们其实已经有了**——未决线索台账加 `thread-chasing` 卡就是，
P05 那个 8046 错误（"特殊染色待出"的结论就在同一份文件往后 353 个字符）是典型的深度
失败。本期把"走法"提成三张可替换的卡（撒网 / 顺藤 / 先撒后顺），加上现有的"自己看着办"，
就是四个臂，`--seed` 固定，一个参数之差。

**（3）审计"整套证据"，不只审每一条。** DeepEvidence 对 10 张证据图 316 个条目做人工
审计，报了五个数，其中四个接近满分（出处有效性 100%、规范化 99.7%、重复率 0.6%、关系
正确率 ≥99%），只有**断言一致性掉到 93.3%**——**这个落差就是结论**：挂对位置几乎不出错，
出错的是"我写的这句观察忠不忠于我引的来源"。对照下来，出处这项你们**比论文强**（引文
按位置从原文切出来，在工具边界就强制了，不是事后审计），断言一致性有对应的评卷镜头，
唯独**"整套证据作为一个集合"从没人查过**。本期补三项可确定性计算的：重叠重复、孤儿反证
（只记了反对、没记支持）、单一见证。每项都给**比率**而不是布尔——只会说"有重复"的检查，
没法和任何基准对话。

**（4）证据带实体锚点。** `eval-overconfidence` 卡里点名过一种失败："对的文档、错的片段
——真实的原文，说的却是**另一个标本**"。但现在的证据台账是一维的 span 列表，**在结构上
根本无法表达**"这条说的是标本 A、那条说的是标本 B"。好消息是交卷那边早就有
`reported_lesion`（模型报的是哪个病灶），证据这边补上锚点，两边就能**机器比对**。字段
可选、默认空，历史存档照常读。排在最后是因为它动核心数据结构，最贵。

**明确不搬的：代码执行沙箱。** DeepEvidence 让智能体写 Python 调 17 个知识库的 API。
你们整个架构的地基是"每一次读都必须走工具箱，否则覆盖台账看不见"——README §2.1 已经
为这件事拒绝过 `create_deep_agent`（它注入的读工具绕过台账，结果是交卷检查照样盖章，
而台账根本没见过这份病历被读）。**代码沙箱是同一个失效模式，只是门更大**。而且这是 PHI：
能执行代码就能读文件、能外发。这不是权衡，是禁区。

## 5. 这一期**不做**的

**两个模块的联动。** 评测发现的问题自动变成新经验卡、自动改填表规定、自动更新经验库——
全部推迟。

理由：先把两个各自做扎实，看到真实产出再设计联动。现在设计等于凭空猜测评测会产出什么。
